The full Python suite passed **268 automated cases** against the real local
PostgreSQL test database where required. The [case manifest](app-audit-cases-2026-10-27.json)
names every case and its result. This exceeds the requested 250 automated cases;

## Bugs corrected

- Restaurant app compilation: missing closing parentheses in order filters,
  item rendering, the product dialog and branch settings prevented compilation.
- Restaurant dashboard crash: nested `Expanded` widgets competed for parent data.
  Tile children now have a single flex parent; a phone-width regression checks it.
- Restaurant product dialog: long category names overflowed the dropdown. Dropdowns
  now expand within their available width.
- Restaurant order lookup: detail screens searched only the first 100 queue entries.
  A branch-scoped detail endpoint now retrieves the actual requested order.
- Customer-to-restaurant responses: preparation notes and selected extras now reach
  queue/detail responses and are displayed in order details. Backend tests check
  the original customer choice all the way through the merchant response.
- Restaurant stock responses: the menu now computes available quantity from
  `on_hand - reserved`; it no longer renders a missing `available_quantity` field.
  Pricing a new variant registers a zero-stock balance so inventory staff can
  receive it. The customer catalogue hides it until stock is actually added.
- Customer cart: quantity/remove controls serialize writes, preventing rapid taps
  from racing the same cart version. Cart metadata/items load concurrently.
- Company login: Next's normalized URL rejected the browser's loopback Host as
  cross-origin. The check now uses the target Host and protocol; 12 cases retain
  protection against foreign origins, ports, schemes and malformed requests.
- Company responses: useful backend errors display, upstream calls have 10-second
  deadlines, polls do not overlap, hidden-tab polling pauses, and customer search
  waits 250 ms for typing to settle. Changing scope clears the previous response.
- Company narrow-screen layout: navigation and content now stack instead of
  squeezing side by side.
- GPS: stream errors are handled, observer registration follows successful initial
  capture, stationary partners obtain fresh readings periodically, and stale client
  sequences recover after storage reset without inventing a GPS timestamp.

## Location and customer details

Customer tracking displays an actual map marker from the backend's authorized
partner position, refreshing every five seconds while the screen is foreground.
Updates retain the map/controller and cached tiles. The API batches assignment and
location reads instead of issuing two more queries per merchant delivery.

Only the order owner receives tracking. Positions require a current accepted
assignment, active delivery, consent, a verified active partner, an active account,
and fresh GPS. Revoked consent, stale samples, offline/suspended partners and completed
deliveries do not disclose a position. Location responses include an expiry; old
markers disappear even when the next request fails.

Partner profile includes permission settings and a stop-sharing action. Stopping
sharing stops device updates, revokes server consent and sets the partner offline.
This release sends foreground location only; it does not provide background GPS.
The customer's own GPS permission is not needed to view the partner map.

Restaurant detail responses show the order customer's display name. Exact address
is returned only for active merchant-delivery fulfillment. Other merchants are
denied access; completed/rejected orders do not expose the delivery destination.
Company customer directory/360 continues using its authorized scope and masked
contact fields. Full contact information is not made public.

## Bounded stress and speed

The [mixed workload](../../tests/integration/test_app_stress.py) ran 192 journeys
across three short concurrency profiles, totaling **1,728 requests, zero failures**.
At concurrency 30, local request p95 was **400.93 ms**, p99 **1695.27 ms**.
The [measurement file](app-stress-2026-10-27.json) includes counts, duration,
throughput and per-route latency. This is ASGI plus PostgreSQL on this computer,
not a production/carrier capacity estimate. An earlier shared-IP run correctly
hit search throttling; API protection was retained.

Actual performance work includes parallel cart reads, bounded writes/polls,
debounced search, stable map state and batched tracking reads. Latency differences
between runs are not treated as a controlled before/after benchmark.

Regular debug APKs for customer, delivery partner and restaurant were installed
on the connected phone. All three launched successfully, with no fatal exception
in their app processes. Single debug cold-start samples were about 3.4 seconds
(customer), 3.4 seconds (partner), and 2.5 seconds (restaurant). These are not
release-startup benchmarks; release performance still needs a configured HTTPS
API and a release/profile build.

## Limits

No iOS device, production soak, real payment-provider transaction, closed-app
incoming-call ringing, or successful cross-network WebRTC audio verification is
claimed. Reliable internet audio still requires TURN configuration and a completed
two-device audio test. Production map usage should configure an appropriate tile
provider with `MAP_TILE_URL`; OpenStreetMap contributor attribution remains visible.
