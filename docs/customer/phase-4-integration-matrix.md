# Phase 4 customer integration matrix

Audit date: 2026-10-26. Scope: `apps/customer_app`, shared Flutter networking/core, `backend/api/v1/routes.py`, schemas, commerce/identity/finance/tracking services and generated API reference.

| Screen / capability | Existing API and contract | Gap found in audit | Planned integration/result |
|---|---|---|---|
| Registration / sign-in | `POST /auth/register` (email + password), `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`, `GET /api/v1/me` | No public phone/OTP registration, phone profile, recovery/reset or terms acceptance endpoint. OTP challenge requires an authenticated user and is sent to the verified email. Local password auth requires configured local signing key; production uses configured OIDC. | Implemented email/password registration and login, secure token storage, refresh-on-401 with one retry, server logout, and a clear OTP limitation. |
| City / address selection | `GET /geo/cities`, `GET /addresses`, `POST /addresses`, `POST /geo/serviceability` | Address requires city ID, freeform text and coordinates. No geocoder, map selection, edit/delete/default-address fields or delivery zone lookup UI contract. | Implemented city-backed manual address entry with coordinates and saved-address selection. No current-location request or geocoding is claimed. Serviceability remains API-authoritative at quote. |
| Merchant home / discovery | `GET /merchants/branches?city_id&limit`, `GET /catalog/categories` | Branch response omits brand type/rating/ETA/offers; no category-aware discovery/search or image metadata. | Connected live branches and added a bounded catalogue search endpoint with keyset cursor. Ratings, offer, ETA and image data remain absent from API. |
| Merchant catalogue / product detail | `GET /merchants/branches/{branch_id}/prices`, `GET /inventory/branches/{branch_id}` | No safe product+variant+stock+current-price join endpoint; no product detail or addon pricing query. | Added authenticated `GET /catalog/products` filtering current prices, approved accepting branches, active products and sellable stock; supports city, branch, category, merchant type, search and cursor. No unpriced addons are offered. |
| Cart | `POST /carts`, `GET /carts/{id}`, `POST/GET/PATCH/DELETE /carts/{id}/items` | Multi-branch lines are supported; no GET cart version/status endpoint. No address/window/method update contract after an item is added. | Added owner-scoped cart state and item names. Cart ID is stored in secure storage; lines reload from backend, quantity changes use expected cart version, and remove/add work against real APIs. Delivery choice and a future window are selected when adding a product. |
| Quote / checkout | `POST /carts/{id}/quote`, `POST /orders/confirm` with `Idempotency-Key` | Taxes/discounts/fees/addons are not calculated by the current quote path. | Quote now returns its server-priced line snapshot; checkout displays returned amounts only and persists a quote-scoped idempotency key across uncertain retries. |
| Scheduling | `GET /merchants/branches/{branch_id}/windows`, `POST /geo/serviceability` | Backend windows are scheduled future windows; no ASAP mode, cutoff/cancellation policy or multiple-slot recommendations. | Use branch-provided windows for each merchant group; no invented ASAP promise. |
| Payment | `POST /finance/sandbox/payment-intents`, authenticated `POST /finance/sandbox/payments/{id}/complete`, `GET /finance/payments/{id}`, signed `POST /finance/sandbox/webhook` | Sandbox requires non-production mode, explicit enablement and a server secret; real gateway remains unconfigured. | Added an owner-checked dev/test-only completion API that signs and processes the existing idempotent webhook path server-side. Production is rejected and no secret reaches Flutter. |
| Orders / detail / history | `GET /orders`, `GET /orders/{id}`, `/merchant-orders`, `/history`, `/delivery-tasks`, `POST /orders/{id}/cancel` | No invoice, review/rating, favorites or reorder API. Cancellation policy is server-side only. | Connect owned order data/history, cancellation with expected version, and repeat-order UI only when current product/stock checks pass. Keep reviews/favorites unavailable absent a verified-order API. |
| Live tracking | `GET /orders/{id}/tracking`, delivery snapshot/timeline/ETA, `POST /realtime/tickets`, authorized `/api/v1/realtime` WebSocket | No Flutter WebSocket integration or map-provider configuration in the app. ETA may return unavailable if routing provider is missing. | Implemented authorized 15-second snapshot polling and retry. Map tiles and WebSocket reconnect are still unconfigured; app only renders server-provided delivery status/location and marks absent locations unavailable. |
| Support / refunds | `POST /support/tickets`; finance refund requires independent approval and is not a customer action | No customer ticket list/status, media attachment or refund request endpoint; direct refunds are intentionally privileged. | Allow ticket creation tied to an owned order. Keep ticket progress/refund status and attachments unavailable until APIs exist. |
| AI suggestions | `POST /ai/recommendations/merchants`, `/products`; `/ai/copilot/status`, `/query` | Recommendation response is deterministic availability/popularity fallback with provenance; copilot provider may be unavailable. | Use only when authenticated, retain `provenance`/`model_status`, and require explicit customer confirmation before any cart/order mutation. |
| Visual / device validation | 40 target screen crops exist in `docs/ui/reference-crops/` | Flutter/Dart/Android SDKs are not installed; backend at `127.0.0.1:8000` did not respond during audit. | Capture what can be rendered; record unavailable Flutter/device/backend checks rather than claiming them passed. |

## Security notes

- All private address, cart, order, payment and tracking calls require the authenticated customer token; backend ownership checks remain authoritative.
- Access and refresh tokens belong in platform secure storage. Never persist credentials/tokens in preferences or source.
- The application never calls privileged finance refund or merchant-order transitions.
- Sandbox completion must be impossible in production and must use server-side signature verification and the existing idempotent webhook path. The app invokes only the authenticated dev/test simulation route; the secret remains server-side.
